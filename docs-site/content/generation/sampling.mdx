`sample_next` receives one row of logits and returns one token id. It runs these steps in this order:

1. If `temperature` is below `1e-6`, return the index of the largest logit and stop.
2. Compute `p`, the softmax of the logits divided by `temperature`.
3. If `0 < top_k < len(p)`, apply top-k.
4. If `top_p < 1.0`, apply top-p.
5. Draw one token from `p` with the generator.

<CodeReference symbol="generate.sample_next" />

At the settings in `config.py`, steps 2, 4 and 5 run. Step 1 does not fire and step 3 is skipped. <PageLink page="generation/autoregressive-generation">Autoregressive Generation</PageLink> lists those settings and shows how the loop calls this function.

**This page has no backward pass.** Sampling runs after the model and computes no loss or gradient, and nothing in `generate.py` calls a backward function. Every number here is an Illustrative Example, except the panel headed Actual Model Output at the end.

In this page's equations, `z` is the logits and the temperature is written with the Greek letter tau. `T` is not used for it, because on this site `T` is the sequence length.

The branch runs only if `0 < top_k < len(p)`. So `top_k = 0` skips it, a negative value skips it, and so does a value equal to or above the vocabulary size.

**How the cut-off is computed.** `np.sort(p)` sorts from smallest to largest, and `[-top_k]` counts back from the end (<CodeLine id="generation.cutoff" />). Repeated values each take a place in that list. With `top_k = 2` and `p` holding three equal largest values, the cut-off is that shared value.

**What happens with ties.** The test is `p >= cutoff` (<CodeLine id="generation.keep-ties" />), not a count. Every token equal to the cut-off stays, so more than `top_k` tokens can remain. Nothing breaks the tie.

The PDF gives a worked example of top-k on p. 14 and no equation, so this concept is marked as derived from the implementation.

**The prefix rule.** `np.searchsorted(cum, top_p)` returns the first position where `cum` is at least `top_p`, counting from 0. The slice then adds 1, so the token at that position is kept (<CodeLine id="generation.prefix" />). The kept tokens are always a run from the top of the sorted order, and the sum of what is kept is at least `top_p`, not at most.

- If `cum` lands exactly on `top_p`, the prefix ends at that token.
- If `top_p` is 0 or below, position 0 already qualifies, so one token is kept.
- If `cum` never reaches `top_p`, for example through rounding at a value just below 1, `searchsorted` returns `len(cum)`, and the slice keeps every token.
- If top-k ran first, its removed tokens are in the sort as zeros. They sit at the end of the order and add nothing to `cum`.

**Ties at the cut.** The code does not treat ties specially here, unlike top-k. If the cut falls inside a group of equal probabilities, some of them stay and some go. `np.argsort(-p)` (<CodeLine id="generation.argsort" />) uses NumPy's default sort, which does not promise an order for equal values, so the code does not define which ones stay. The number of tokens kept does not depend on that order.

The PDF gives a worked example of top-p on p. 15 and no equation, so this concept is marked as derived from the implementation.
