### m and v

The class keeps two arrays per parameter, both starting at zero (<CodeLine id="adam.init-moments" />). In general, these are called the first moment and the second moment. The code calls them `m` and `v`:

- **`m` is momentum.** It is a running average of the gradient, so it holds the direction of recent batches. `beta1` is how much of the old average it keeps on each step.
- **`v` is the second moment.** It is a running average of the squared gradient, so it holds the typical size of the gradient for each number. `beta2` is how much of the old average it keeps.

The update divides `mhat` by the square root of `vhat`. A number whose gradient is always large gets a large `vhat`, and the division brings its move back to about `lr`. So does a number whose gradient is always small. This is what the comment on that line says: every number moves about `lr` per step.

Decay is decoupled: it is added to `update` after `m` and `v` are computed, so it never enters those averages, and clipping never sees it. ### Which parameters get weight decay

The rule is one line, `params[k].ndim >= 2` (<CodeLine id="adam.ndim" />). The rule depends only on the number of dimensions, so the two embedding tables get decay too, although `config.py` calls this "weight matrices". The table lists every name `init_params` creates. "Weight decay" comes from running the real `Adam.step` on all ones with zero gradients, where only decay can change a value.

Read the first column of each pair against the second. `w` and `b` start equal and get the same gradients, so `self.m[k]` and `self.v[k]` stay equal. They differ only in `update`, because `w` also has `self.wd * params[k]`. The values for `b` round to the `0.9000` and `0.8068` that `test_adam_two_step_hand_trace` asserts.

On the first step, the correction makes `mhat` equal to `g` and `vhat` equal to `g` squared. So `update` before decay is close to the sign of `g`, whatever its size. A test checks this (<CodeLine id="adam.first-step" />).

`train.main` adds one to `step` before calling the schedule (<CodeLine id="loop.step-count" />), so step 0 is what the function would return, not a value training uses.

**`lr_max` is reached at the last warmup step.** At step `warmup_steps`, the test `step <= warmup` is still true (<CodeLine id="schedule.warmup-if" />), so the function returns `lr_max * step / warmup` (<CodeLine id="schedule.warmup-return" />), which is exactly `lr_max`. The next step is already on the cosine and slightly lower, as the table shows. The comment on `lr_max` in `config.py` says "reached right after warmup" (<CodeLine id="schedule.config-comment" />). This page follows the code.

The function has two results. It changes `grads` in place, and it returns the norm from before clipping as a Python float. `train.main` stores that as `norm` and prints it as `|g|` (<CodeLine id="train.log" />). So `|g|` can be above `grad_clip`, although the gradients that reach `opt.step` have a length of at most `grad_clip`.

It runs right after `batch_loss_and_grads` and before the learning rate and `opt.step`, so `m` and `v` only ever see clipped gradients.
